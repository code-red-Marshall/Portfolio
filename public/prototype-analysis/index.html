At a glance

~300max recipients per fire (60s ceiling)
4external systems: Vercel, Supabase, Meta, Groq

Stack

  • Next.js 16.2 App Router, React 19, Tailwind 4 + shadcn, running on Vercel serverless
  • Supabase: Postgres (service-role client), Auth (email + password, JWKS), Storage (template-media)
  • Meta WhatsApp Cloud API through lib/meta-waba.ts, pinned to Graph v19.0
  • Groq gpt-oss-120b for "Draft with AI", with structured output and a single repair round

Core flows

  • Audience: CSV parsed in the browser, field roles detected, rows uploaded in batches, then finalized (dedupe, sendable count)
  • Template: compose or AI draft, server-side validateDraft(), submit to Meta; status comes back by webhook, with Sync as a fallback
  • Campaign: wizard maps {{vars}} to CSV columns, fire runs the guards, sends in the background, and receipts come back by webhook

Findings, ranked

SeverityFindingWhereFailure scenario
Critical Failed campaigns are invisible to the double-send guard. audience_messaged_phones only counts campaigns whose status is Sending or Completed. supabase-audience-selection.sql:44, fire/route.ts:132 A 1,000-row send hits the 48s budget after ~300 messages and is marked Failed. Re-firing it, firing a new campaign on the same audience, or using "Select unsent" all treat those ~300 people as never messaged, so they get the message again with no warning.
Critical Webhook signature check fails open. If META_APP_SECRET is unset, every POST is accepted. The comparison is also a plain ===, not constant-time. lib/meta-waba.ts:463,466 If the env var is missing on a Vercel project, anyone can POST fake delivered/read/failed events or template APPROVED events, which corrupts counters and template status.
High Silent simulation mode. If any of the three META_* vars is missing, sendMessage returns simulated and the fire loop counts that as delivered and read. lib/meta-waba.ts:405, fire/route.ts:332 On a misconfigured deployment (see the two-Vercel-projects gotcha), a campaign shows 100% delivered and read while nothing was sent.
High Throughput ceiling, no resume. maxDuration 60, a 48s budget and 8 workers at ~1.1–1.5s per send cap one fire at roughly 260–350 recipients. fire/route.ts:15,24,34 Any audience above ~300 always ends Failed and part-sent. Combined with the first finding, the only way to finish the send is one that re-messages people. This needs a cursor/queue (resume from logs), or a status like Partial that the guard counts.
High Webhook counters aren't idempotent. Each status event runs increment_campaign_counts(+1) without checking the log's previous status. webhooks/whatsapp/route.ts:69,75,104 Meta retries webhooks on slow or failed responses. A redelivered "delivered" event double-counts, so dashboards can show more than 100%. Also, a "failed" event after "delivered" increments failed without decrementing delivered.
Medium Blank personalization still sends. An unmapped placeholder or blank cell resolves to "". lib/audience-schema.ts resolveField A row with an empty name goes out as "Hi ,". Approved in Phase 1 on 2026-08-11 but not built yet.
Medium Access control is flat. Every route uses the service-role client (RLS bypassed), and the @vantagecircle.com signup rule is only enforced in the browser. lib/supabase.ts, login/page.tsx:20 Anyone who calls Supabase signUp directly with any email gets full power, including firing to real employees.
Medium Template id churn. Sync upserts onConflict: "name". Rows keep their id when found, but a rename or delete-and-recreate at Meta can still orphan campaigns.template_id. templates/sync/route.ts:58 A campaign's details page loses its template link, so joins fall back to matching on name.
Medium Graph API pinned to v19.0. Meta retires versions about two years after release, and v19.0 shipped in January 2024. lib/meta-waba.ts:5 Worth checking against Meta's changelog now. Calls to an expired version get auto-upgraded or rejected.
Accepted Opt-outs recorded, not enforced. STOP replies are written to opt_outs, but the fire route never reads it. webhooks/whatsapp/route.ts:114 You declined this on 2026-08-19 because each send is a one-off from a fresh file. The Scala module now enforces STOP, so the prototype is the weaker of the two.

What's solid

Send-path engineering

  • after() keeps the invocation alive after the 202 (fixes the frozen-at-"Sending" bug)
  • The atomic claim is a conditional UPDATE … NOT IN (Sending, Completed), so two tabs can't both fire
  • fetchWithRetry: 15s timeout, jittered backoff, retries only on 429/5xx, and unwraps the error cause chain
  • Logs are batched per 50 and upserted on a pre-generated id, so a lost response can't duplicate rows

Safety & resilience

  • The fire route re-checks the session with Supabase Auth (getUser()); other routes verify JWTs locally against JWKS
  • Overlap is checked per recipient and needs an explicit allowDuplicate to override (except for the Failed gap above)
  • Missing columns (42703) degrade gracefully instead of taking down the send path
  • Reads page past Supabase's 1,000-row select cap, and Meta's template rules are re-validated on the server
